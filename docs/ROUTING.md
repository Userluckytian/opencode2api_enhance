# 路由机制说明（Route Modes）

> **历史文档（v1.9 及以前）**：实例池与节点池已在 v2.0.0 移除，本文仅作历史参考。
> 现行架构与路由口径见 `CHANGELOG.md` v2.0.0 与 `docs/PLUGIN-PROVIDERS.md`。

> 本文档说明 opencode2api 统一网关的路由模式：**智能模式（smart，默认推荐）**、**负载均衡（round_robin）** 和 **故障转移（failover）**。
> 面向使用者与开发者，涵盖各模式的行为、参数与配置方式。

---

## 一、三种模式总览

| 模式 | 别名 | 核心思想 | 适用场景 |
|------|------|---------|---------|
| **智能模式（默认推荐）** | smart | 故障转移 + 超时检测 + 健康计数淘汰（含质量分/竞速等性能模式能力，见 PERFORMANCE-MODE.md） | **生产推荐**，兼顾稳定与容错 |
| **负载均衡** | round_robin | 每次请求轮询分发到不同实例 | 节点都健康、希望均摊流量 |
| **故障转移** | failover | 锁一个实例用，失败才换下一个 | 简单直接的历史模式 |

---

## 二、负载均衡（round_robin）

### 行为
- 维护一个游标，**每次请求游标 +1**，请求分发到对应实例
- 跳过"临时不可用"的实例（见下）

### 优点
- 流量均匀分散到所有实例
- 没有"单点压力"

### 缺点
- 可能命中异常实例（健康度低/冷却中的节点轮到时仍会被尝试）
- 对"免费额度"型节点不友好（均匀轮询会让每个节点都快速消耗额度）

### 配置
```json
{ "route_mode": "round_robin" }
```

---

## 三、故障转移（failover）

### 行为
- 维护一个游标，**成功不动游标**，**失败才切换到下一个健康实例**
- 锁定一个实例持续使用，直到它出错

### 流程
```
实例1 可用 → 一直用
   ├─ 故障(429/401/5xx/连接失败) → 切换实例2
实例2 可用 → 一直用
   ... 直到最后一个 = 1 轮
```

### 优点
- 稳定：锁一个健康实例，减少无谓切换
- 简单：逻辑直白

### 缺点
- **没有超时检测**：如果实例"挂起"（连接建立了但迟迟不吐数据），会一直干等
- **没有健康记忆**：反复失败的实例会被反复尝试，浪费请求

### 配置
```json
{ "route_mode": "failover" }
```

---

## 四、智能模式（smart，默认推荐）：failover + 健康计数

### 行为
在**故障转移**基础上，增加：
1. **超时检测**（首字 / 静默）
2. **故障计数**（跨轮累计，3 次淘汰）
3. **成功清零**（恢复健康）

### 完整流程
```
实例1 可用 → 一直用
   ├─ 故障(429/401/5xx/连接失败) → 计数+1 → 切换实例2
   ├─ 超过 X 秒无响应（一个字都没收到）→ 计数+1，错误"延迟>X s" → 切换实例2
   └─ 回复到一半，卡住超过 Y 秒 → 计数+1 → 切换实例2
实例2 可用 → 一直用 ... 直到最后一个 = 1 轮
```

### 健康计数规则
- **计数 +1**：每次故障/超时
- **满 3 次** → **停止该实例**（不从池中移除），把错误信息展示给用户
- **用户手动重启实例** → 计数清零（重新开始）
- **某轮正常** → 计数清零（后续异常从 1 重新计数）
- 计数**跨轮累计**（一轮 = 从实例1 依次用到最后一个实例）

### 时间参数（可配置）
| 参数 | 默认值 | 白话含义 |
|------|--------|---------|
| **首字超时（TTFT）** | 10s | 发请求后干等 X 秒一个字没收到 → 换实例 |
| **静默超时** | 5s | 回复到一半，卡住 Y 秒没新内容 → 换实例 |
| **总超时** | 不设 | 长任务不限制（避免掐断正常长回复） |

### 为什么推荐
- **稳定**（继承故障转移的"锁节点"）
- **不干等**（超时检测兜底）
- **自我修复**（计数淘汰坏实例 + 重启恢复）

### 配置
```json
{ "route_mode": "smart" }
```

> 注：`smart` 是内置默认值（`core/manager/gateway.go`），不配置即生效；
> `failover` / `round_robin` 仍可显式选择。

| 参数 | 默认值 | 说明 |
|------|--------|------|
| route_mode | `smart` | `smart` / `failover` / `round_robin` |

## 六、并行预热（快速故障跳转）【优化方向】

### 需求
用户发起一次对话请求时，**并行探测后续实例**（预热），当前实例超时不回复时，**快速转移到已探测通过的实例**，避免现场串行探测的延迟。

### 机制
```
用户发起对话请求
  ├─ 实例1 开始正常请求
  └─ 【并行】预热游标之后的 X 个实例（用真实最小对话请求探测）
如果实例1 超时不回复 → 查预热缓存：
  ├─ 缓存里有健康实例 → 立即切换到该实例（快）
  └─ 缓存里没有健康实例（这一批都不行）→ 跳过这一批，请求下一批的第一个
      且这一批全部标记故障 +1（错误标记为"延迟>X s"）
```

### 规则
- **预热范围**：游标之后的 X 个实例（不是全池），X 可配置
- **探测方式**：真实最小对话请求（`max_tokens:1` 级别，真实可靠，会消耗少量额度）
- **缓存**：预热结果保留 N 秒（默认 15s），期间复用，避免每请求都探测
- **切换**：超时 → 用缓存健康实例；缓存空/无健康 → 跳过这批，游标跳到下一批第一个
- **计数**：预热失败的实例标记 +1（"延迟>X s"），满 3 次停止实例（与主规则一致）
- **下一批**：游标直接跳到下一批的第一个实例，继续预热后续

### 配置项（设置页）
| 配置 | 默认 | 文案 |
|------|------|------|
| 并行预热数量 | 待定 | 对话时，并行预热实例的数量【】，为故障做快速跳转 |
| 预热缓存时长 | 15s | 预热结果缓存时长：【】秒 |

## 七、auto 虚拟模型（已落地，2026-08-17）

> 面向用户的「一个模型名用整个池」入口：客户端只填 `model: "auto"`，网关自动选模型 + 失败降级。
> 配置入口：**实例池页 → 右上齿轮 → 「auto 模型 · 智能选路」折叠区**（默认关闭；权重与上下文在同一张表逐模型配置）。

### 1. 选择算法（一次请求的完整链路）

```
model:"auto"（OpenAI / Claude / Responses 三入口，含流式）
  ├─ ① 候选集：目录中免费模型，权重>0（0=永不参与；缺省 5；按模型粒度，
  │        同模型跨实例同权重——实例差异交给既有 smart/failover 池路由）
  ├─ ② 上下文护栏：est(请求 token 保守估算) ≤ 有效上限 × 0.9 过滤，
  │        有效上限 = min(用户配置, 失败学习值, 保守默认 128k)
  ├─ ③ 打分：score = (权重/10) × 实测成功率（10 分钟滑窗，无样本=1.0 不惩罚冷启动）
  ├─ ④ 按策略选主选 + 生成降级链（整链已过护栏）
  │     · 均衡 balanced（默认）：平滑加权轮询（SWRR），分布 ∝ score，额度按权重分摊
  │     · 速度优先 speed：权重≥5 的候选里选实测延迟最低者（无实测回退按分）
  │     · 能力优先 quality：严格按分锁定最高权重者，失败才沿链降
  ├─ ⑤ 请求失败/超时（429/5xx/传输错误）→ 反馈记一笔 → 链上下一个，客户端无感
  │        （有界：单请求最多切换 3 个模型；流已对外吐字节后不换模型，续写沿用原模型）
  └─ ⑥ 调用日志 auto_pick 事件：选了谁 / 策略 / 估算 token / 降级链
```

### 2. 上下文护栏（三道防线）

| 防线 | 机制 | 说明 |
|---|---|---|
| 请求侧 | 保守 token 估算 | est = Σ max(字节/4, 字符/2)——中文≈0.75 tok/字、英文≈0.25 tok/字，均偏保守；图像部件不计入 |
| 模型侧 | 有效上限 = min(三者) | 用户配置（UI 每模型可填真实值）；失败学习值（上游报上下文类错误自动收紧，填错会被修正）；保守默认 128k |
| 选择侧 | 整链过滤 | 主选与全部降级候选都必须装得下本次对话（留 10% 给输出）；全超限按最大上下文兜底并在日志标记 |

附带收益：对话随轮次增长，auto 会自然从小上下文快模型迁移到大上下文模型——「短对话抢速度、长对话保能力」。

### 3. 配置与生效

- 存储：config.json 的 `auto_model` 键（enabled / strategy / weights / context_windows），
  管理端 `GET·POST /api/admin/auto-model`；与 providers 同款「AppConfig × Config 双结构」生存策略。
- 生效：保存即传播全部子进程配置（runtime/*/opencode2api.json），运行中子进程 3s 热重载；
  停着的实例下次启动自动带上。`/v1/models` 仅在开启时于顶部列出 `auto`（关闭即消失，防客户端缓存无效名）。
- 用量与统计：token 用量按实际选中的具体模型记账（统计页不出现虚拟行）；反馈滑窗按（模型×实例）记录，
  auto 与非 auto 流量共同喂养。
- 反馈窗口：10 分钟、每键 64 条封顶；模型分 = 跨实例聚合成功率（成功样本均延迟供速度策略）。

### 4. 决策记录（2026-08-17）

- 权重按**模型粒度**而非（实例×模型）对：实例差异已由池级质量加权路由覆盖，按对配置徒增 16 格负担。
- auto 降级只发生在**返回客户端之前**；流中（streamWithResume）沿用同一模型重试，保证对话连贯。
- 非直接落地的历史决策（跨模型回退需配合质量分、模型×实例矩阵不做主路径）与本实现一致——
  auto 的降级链正是「用户偏好（权重）+ 质量分（实测反馈）」的组合，不满足权重的模型根本不进链。

## 八、后续优化方向（auto 之外）

### 1. 质量分排序（参考 model-gateway）
- 为每个实例维护**滑动窗口可用率 + 平均延迟**（窗口 20 条）。
- 路由选择按 `(-可用率, 延迟)` 排序，坏实例自动降权、好了自动回升。
- 注意：可用率由**探测**驱动、失败计数由**请求**驱动，两套信号分离。

### 2. 流预检 Prime（参考 enhance_2）
- HTTP 200 后 12s 内必须见到**真实模型输出**（非空 delta/text/reasoning/tool_calls），否则判死流 → 标记失败 → 换候选重试，**客户端无感知**。
- 与流内超时（TTFT/静默）互补：prime 挡"建流前死"，流内超时挡"建流后挂"。

### 3. 巡检预算（参考 model-gateway）
- 每日巡检次数预算 + 每日强制巡检 + 手动全检重置计时，防止探测打爆免费 API 额度。

### 4. 跨模型回退（需谨慎，评估后做）
- 模型级回退（此模型 429 换下一个免费模型）**仅配合质量分**：只回退到质量分接近的模型。
- ⚠️ 若免费模型质量差异悬殊（只有一个好用），无脑跨模型回退 = 垃圾模型浪费额度，**弊大于利，不单独做**。

### 5. 模型×实例矩阵（不建议单独做）
- ⚠️ 已评估：仅当候选模型质量接近时才有意义；否则是"垃圾模型×好实例"的无效尝试。**不列入主路径**，仅作为质量分排序的兜底。

## 九、决策记录（利/弊评估）

> **既定前提**：免费模型质量必然参差不齐（有的好用、有的拉胯）。所有涉及"多模型选择"的优化都必须基于这一现实评估——**不做**任何"假设所有模型质量接近"的设计（如无脑跨模型回退、模型×实例矩阵）。此前提记录于此，非现阶段实施，供未来优化参考。

| 候选方案 | 利 | 弊 | 结论 |
|---------|----|----|------|
| 跨模型回退链 | 多模型可用时提升可用性 | 单好模型时垃圾模型浪费额度 | 配合质量分才做 |
| 模型×实例矩阵 | 全覆盖尝试 | 质量悬殊时纯浪费 | 不做主路径 |
| auto 模型 + 权重 | 用户友好、兼顾速度质量 | 需实现质量分 | ✅ 已落地（见第七节） |
| 质量分排序 | 自动降权坏节点 | 需探测数据积累 | ✅ 做 |
| 流预检 Prime | 客户端无感挡死流 | 与现有超时重叠需整合 | ✅ 做 |
| 巡检预算 | 防探测打爆额度 | 实现成本 | ✅ 做 |

## 出站链路：谁走 sing-box，谁直连（⭐ 修改前必读）

> 本节回答一个高频困惑："我的模型到底走不走 sing-box？"以及维护者改动调用链前必须知道的分层语义。
> 结论先行：**出站走不走代理由「进程内 Tier 判定 + 该进程配置的 SOCKS 池」共同决定**，两者缺一不可。

### 1. Tier 判定（每个厂商自己决定）

| 厂商/模型 | Tier | 含义 |
|---|---|---|
| opencode 免费模型（内建） | **恒 TierFree** | 永远走代理池，不看任何开关 |
| **自定义模型源** | `via_proxy=true` → TierFree；`false`（默认）→ TierPaid | 仅此开关控制（`vendors/custom` 的 `tier()`），与实例池 `route_mode` **互不相干** |

TierFree = `Transport.Client` 返回 SOCKS 池客户端；TierPaid = 裸直连客户端（`socks.go` 的
`getHTTPClientForTierWithProxy`：TierPaid 恒返回直连）。**改 tier 语义前先想清楚会不会把内建免费模型改成直连**（上游会按 IP 风控）。

### 2. 每个进程的"SOCKS 池"指什么（同样关键）

| 请求打到 | 该进程的池 | 内建模型走 | 自定义 via_proxy=true 走 | false 走 |
|---|---|---|---|---|
| **实例端口**（独享/池成员，40100+/44200+） | `active_socks5` = 本实例 sing-box | 本实例节点 ✓ | 本实例节点 ✓ | 直连 |
| **统一网关**（+80） | `socks5_proxies` = 入池成员 sing-box 列表（round_robin/failover/smart） | 成员节点 ✓ | 成员节点 ✓ | 直连 |
| **管理端口**（40000/44100，面板 UI 同源） | **没有配置池** | **直连！** | **直连！** | 直连 |

⚠️ 管理进程虽然也监听 `/v1`，但它的 config.json 不含 socks 池——**想走代理请打网关或实例端口**。
日志页里"全部直连"的第一排查项就是：请求打的是哪个端口 + 该进程配置里 socks 三键（`socks5_proxies` / `active_socks5` / `route_mode`）是否还在。

### 3. 「上游代理出口」（E1）会接管 TierFree 的含义

设置页配置 `upstream_proxy` 后，实例/网关的 TierFree 出口全部改指该地址（跳过 sing-box 节点）。
此时"走 sing-box"实际是"走那个上游代理"——**代理一死，勾了代理的自定义源和内建模型一起 502**
（典型症状：`socks5 connect 127.0.0.1:xxx: connectex: ... actively refused`）。

### 4. 网关配置文件的多写者警示（维护者）

`runtime/_unified-gateway/opencode2api.json` 存在多个写者，**任何人改动这里都必须遵守**：

- 写者清单：Go 管理器 `buildRouterCfg`（恒写完整形状，含 socks 三键）、Rust 壳 `sync_gateway`
  （`opencode_cfg.rs`，同样恒写完整形状）、网关进程启动时的 AppConfig 自写回盘、
  自定义源传播补丁（`patchProvidersFile`，map round-trip 保留既有键）
- **新写者必须**：① 原子写（tmp + rename）；② 保留既有键，只增改自己的键段
- 典型事故：配置文件丢失 socks 三键 → 网关全直连（日志 `route_mode: smart` 是**内置默认值**，
  出现它 + 全部"直连"即配置丢段症状）。**恢复方法**：实例池页做一次成员变化（停/启一个池成员
  或切路由模式）触发网关配置全量重生成 + 子进程重启

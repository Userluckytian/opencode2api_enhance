# 插件资源与稳定性要求（宿主强制约束）

> 适用对象：所有以 `--provider-serve` 形态运行的插件供应商
> 契约基线：[`PLUGIN-PROVIDERS.md`](PLUGIN-PROVIDERS.md) §10（功能契约，P0 拒载）
> 能力菜单：[`PLUGIN-CAPABILITIES.md`](PLUGIN-CAPABILITIES.md)（A~J 100+ 项）
> 本文补的是**前两份文档缺失的那一维**：长期运行时的资源纪律。
> 建立日期：2026-11-11

---

## 零、为什么需要本文

`PLUGIN-PROVIDERS.md` §10 规定了「插件必须提供什么」，`PLUGIN-CAPABILITIES.md` 的 I10 只写了
一句「内存/句柄/并发上限 — 长时间运行不涨」，**没有任何可执行判据**。实际后果：

- 宿主对插件**不做任何资源限制**（全仓无 Job Object / cgroup / rlimit），插件涨多少内存、
  泄漏多少句柄、开多少 goroutine，宿主都不会拦，只会跟着一起变慢或被系统 OOM 杀掉。
- 插件是**长期驻留**进程（典型运行数天到数周），不是一次性 CLI。一次请求泄漏 1KB，
  一天 10 万请求就是 100MB。
- 宿主与插件是**同机不同进程**，插件拖垮的是整台机器，不是它自己。

本文给出的每条要求都标注了**宿主侧的真实参数**（有代码位置），以及**如何验证**。
无法用宿主参数兜底的部分，明确写「插件自己负责」。

## 一、宿主提供的真实边界（插件必须知道的硬参数）

这些不是建议，是宿主的实际行为。插件设计必须按这些数字来。

| 参数 | 值 | 宿主实现 | 对插件的含义 |
|---|---|---|---|
| 启动就绪超时 | **15s** | `defaultStartupTimeout`，`manager.go:44` | 从 spawn 到打出首个状态行的总预算。冷启动要预热（下模型、连上游、起浏览器）的插件，必须把重活放到 `ready` 之后 |
| 崩溃重启退避 | **0s → 5s → 15s → 30s** 封顶 | `manager.go:1288` | 连续崩溃时宿主最多等 30s。**插件不得自己再加一层重启循环**，否则两层叠加成抖动 |
| 「健康运行」判定阈值 | **30s** | `defaultStableReset`，`manager.go:49` | 存活满 30s 才把退避计数归零。启动即崩的插件会快速耗尽四次机会 |
| 模型清单查询超时 | **5s** | `defaultModelTimeout`，`manager.go:48` | `/v1/models` 必须 5s 内返回，且响应体被 `io.LimitReader` 限到 **1MB**。模型多的大目录要注意体积 |
| 模型清单轮询 | 由宿主按需触发 | `fetchPluginModels` | 插件侧不要自己做定时全量重扫；宿主会在需要时来拉 |
| 孤儿回收扫描周期 | **15s** | `orphanReapInterval`，`manager.go:61` | 见 §六：插件后代进程的存活由这个周期兜底，不是立即 |
| 日志环形缓冲 | **500 行 × 单行 4096 字节** | `pluglogs.go:35-38` | 超出部分宿主**直接丢弃**（不是轮转）。插件不能指望「打日志留证据」，关键错误必须进状态行或 `data/` 文件 |
| stdout/stderr 消费 | 两条常驻 goroutine，读到 **EOF** 才结束 | `manager.go:970-971` | 宿主一定读完。**但插件必须保证子进程退出时两个管道都关闭**，否则 goroutine 悬挂（见 §三.4） |
| 资源限制 | **无** | 全仓无 Job Object / cgroup / rlimit | 内存、CPU、句柄、goroutine 全靠插件自律 |
| 插件请求转发超时 | **无总超时**（流式设计），靠 `context` 取消 | `contract.go:156` `DirectTransport`、`remote.go:249` | 长推理流不能被切断是刻意设计。**因此超时必须由插件对自己上游设置**，否则一个挂死的上游会让请求永久占着连接与 goroutine |

> 时间/字节数若与代码不一致，以代码为准；本文档随宿主参数变更同步更新。

## 二、内存纪律（P0，最高优先级）

插件内存是**唯一没有兜底**的资源。宿主不限制、不监控、不重启（除非进程自己崩）。

### 2.1 必须做到

| # | 要求 | 判据 |
|---|---|---|
| M1 | **流式响应必须逐块转发并立即释放**，不得把整个 SSE 流缓冲成一个字符串再发 | 10 并发 × 1MB 流式响应，峰值 RSS 增量 < 50MB |
| M2 | **HTTP 响应体必须 `defer resp.Body.Close()`**，且非流式路径用 `io.Copy(io.Discard, ...)` 读尽或显式关闭，否则连接无法复用、底层缓冲不释放 | `goleak` 与 `net/http/pprof` 无持续增长的 `http.Client` 相关对象 |
| M3 | **不得在包级变量/全局 map 中无限累积**（账号缓存、请求历史、错误记录、去重表）。必须使用时要有**容量上限 + 淘汰策略** | 长跑 24h 后该 map 的 `len()` 稳定，不随请求数线性增长 |
| M4 | **请求级的大对象（请求体、响应体、base64 图片）不得跨请求持有**，处理完即让其可回收 | pprof heap 采样中无跨请求的 `[]byte` 大块 |
| M5 | **单请求内存上限自查**：请求体 > 32MB 应拒绝而非全量读入 | 构造 100MB 请求体，插件返回 4xx 而不是 OOM |
| M6 | **不得缓存全部历史模型目录/账号快照的多份副本**（每次刷新新建一份、旧的不释放） | 连续触发 20 次模型刷新，RSS 不阶梯式上涨 |

### 2.2 参考基线（2026-11-11 现场实测）

同机 10 个运行中插件的 `WorkingSetSize`：

| 插件 | RSS |
|---|---|
| qw2api | 73.7 MB |
| buddyhub | 72.6 MB |
| xhx | 72.0 MB |
| mmxproxy | 65.3 MB |
| loomy | 55.5 MB |
| grok | 49.5 MB |
| devin | 48.4 MB |

**基线：常驻 50~75MB 属正常区间**（Go 运行时 + 依赖库本身就有这个量级）。

**判定「泄漏」的口径**：
- 稳定运行 24h 后 RSS 相比启动后 1h 的基线**增长 < 30%** → 正常（Go GC 会让 RSS 缓慢上探后回落）
- 增长 30%~100% 且仍在涨 → 观察，需提供 pprof 证据
- **持续单调上涨、无回落、翻倍以上** → 判定泄漏，必须修

> 注意：RSS 不等于堆内存。Go 的 RSS 包含未归还给系统的 arena。判泄漏要看
> `runtime.MemStats.HeapInuse` 或 pprof `inuse_space` 的**趋势**，不要只看任务管理器。

### 2.3 自测方法（插件作者必做）

```go
// 1) 开启 pprof（仅调试构建，或用一个只有本机可达的独立端口）
import _ "net/http/pprof"
go http.ListenAndServe("127.0.0.1:6060", nil) // 绝不对外
```

```bash
# 2) 压测前后各采一次，比较 inuse_space 与 goroutine 数
go tool pprof -top http://127.0.0.1:6060/debug/pprof/heap
go tool pprof -top http://127.0.0.1:6060/debug/pprof/goroutine
```

判据：**压测 1000 次请求后，goroutine 数应回到压测前 ±10 以内**；
`inuse_space` 的 top 项不应随请求数增长（缓存类对象应有固定上限）。

## 三、Goroutine 与并发纪律（P0）

Go 插件最常见的泄漏是 goroutine 悬挂：持有它的 channel/连接永远不关闭。

### 3.1 每个 goroutine 必须有明确的退出路径

| # | 要求 |
|---|---|
| G1 | **禁止 `go func(){ for { ... } }()` 这种无退出条件的常驻循环**。必须有 `ctx.Done()` 分支或 `stop chan struct{}` |
| G2 | 每个 `go` 语句的附近必须能回答「它在什么条件下退出」。回答不了就是泄漏 |
| G3 | 启动的后台循环（轮询配置、刷新号池、清理缓存）必须在插件收到退出信号时停止 |
| G4 | **`time.Ticker` / `time.Timer` 必须 `defer Stop()`**，否则底层 runtime timer 不释放 |
| G5 | **每个请求派生的 goroutine 必须与请求同生命周期**：请求 ctx 取消时它也要退出 |

### 3.2 并发度必须有上限

| # | 要求 | 判据 |
|---|---|---|
| G6 | 上游并发必须有信号量/worker pool 上限，**不得「每个请求一个无限 goroutine」** | 1000 并发打进来，goroutine 峰值有天花板（如 ≤ 并发上限 × 常数），不是 1000+ |
| G7 | 批量操作（刷新全部账号额度、检查全部号池）必须限并发（建议 4~8） | 200 个账号刷新，goroutine 峰值 < 50 |
| G8 | 长任务（注册、签到）必须有**任务级超时 + 单账号超时** | 上游挂死时任务能结束并报错，不是永久 running |

### 3.3 channel 与锁

| # | 要求 |
|---|---|
| G9 | 向无缓冲 channel 发送必须有 `select { case ch <- v: case <-ctx.Done(): }`，否则接收方退出后发送方永久阻塞 |
| G10 | 锁的临界区不得包含网络调用 / 磁盘 IO / 可能阻塞的操作（这是锁竞争与死锁的主要来源） |
| G11 | 禁止在持锁状态下调用可能回调到自身的代码（`OnChange` 类回调） |

### 3.4 stdout/stderr 写端（宿主强相关，易踩）

宿主对插件 stdout、stderr 各起一个 goroutine 读到 **EOF**。这意味着：

- 插件**必须保证退出时两个管道都被关闭**。Go 里父进程 `cmd.StdoutPipe()` 得到的读端，
  在子进程所有持有写端的句柄关闭后才 EOF。
- **反例**：插件 fork 一个孙进程（node、msedge、mihomo），孙进程继承了 stdout/stderr 句柄。
  插件自己退出后，孙进程仍持有写端 → 宿主读到 EOF 的时间被无限推迟 →
  **两个 goroutine 悬挂，且 `cmd.Wait()` 永不返回**。
- **要求**：插件拉起孙进程时**必须显式重定向孙进程的 stdout/stderr**（到文件或 `os.DevNull`），
  绝不能让它继承插件的 stdout/stderr。

```go
// 正确：孙进程输出重定向到文件或丢弃，不继承父进程标准流
cmd := exec.Command("mihomo", "-f", cfgPath)
logFile, _ := os.OpenFile(filepath.Join(dataDir, "mihomo.log"),
    os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0o644)
defer logFile.Close()
cmd.Stdout = logFile
cmd.Stderr = logFile
// cmd.Stdout = nil 是错的 —— nil 表示"接到 /dev/null"，但这依赖平台实现；
// 显式给 *os.File 或 io.Discard 才没有歧义
```

> 这条同时解释了为什么宿主必须有 `/T` 树杀（见 `MASTER-orphan-governance.md`）：
> 只杀插件不杀孙进程，孙进程会一直持有管道和端口。

## 四、文件句柄与网络连接纪律（P1）

| # | 要求 | 判据 |
|---|---|---|
| H1 | 每个 `os.Open` / `os.Create` 必须配对 `defer f.Close()`；循环内打开的文件**必须在循环体内关闭**，不得攒到函数结束 | 长跑后 `lsof`/`handle.exe` 计数稳定 |
| H2 | 每个 `http.Response.Body` 必须关闭（同 M2） | 无 `TIME_WAIT` 堆积、无 fd 增长 |
| H3 | 自定义 `http.Client` 必须复用（**不要每次请求 `&http.Client{}`**），否则连接池与空闲连接永不回收 | `http.Transport` 实例数稳定（不是随请求增长） |
| H4 | 长连接/SSE 上游必须设 `IdleConnTimeout`，避免上游半死连接长期占用 | 上游断开后连接在有限时间内被清理 |
| H5 | 浏览器类插件（chromedp/msedge）必须保证进程与临时 profile 目录在退出时清理；profile 目录要有 TTL | `data/` 体积不随时间无限增长；无残留 `msedge.exe` |

### 4.1 浏览器型插件的额外要求（qw2api / devin 类）

| # | 要求 |
|---|---|
| H6 | 每个插件实例只允许**一个**浏览器进程树；重启前必须确认旧进程已退出（否则端口/profile 冲突） |
| H7 | 浏览器 profile 目录必须在插件自己的 `data/` 下，文件名带实例/时间戳，**不得共用** |
| H8 | 浏览器进程必须作为插件的**直接子进程**启动（这样宿主 `/T` 树杀能覆盖）；**不得用 `start`/`nohup`/`setsid` 脱离** |
| H9 | 面板上的「关闭浏览器」必须真正 kill 进程树，不是只置标志位 |

## 五、超时纪律（P0）

宿主对转发给插件的请求**不设总超时**（为了不切断长推理流）。因此**所有超时必须由插件对自己上游设置**。

| # | 位置 | 建议值 | 理由 |
|---|---|---|---|
| T1 | 连接建立（dial） | 10~15s | 上游 DNS/握手挂死时快速失败 |
| T2 | 响应头等待（`ResponseHeaderTimeout`） | 30~60s | 上游受理但不返回时不能无限等 |
| T3 | 首个 SSE 事件 | 30~60s | 已建立流但无数据 = 上游半死 |
| T4 | 非流式整请求 | 120~300s | 按上游特性定，但**必须有** |
| T5 | 流式请求 | **不设总超时**，但必须设「相邻事件间隔」超时 | 长推理正常，卡住不正常 |
| T6 | 账号刷新/签到等后台任务 | 单账号 30~60s，整批有总预算 | 防止一个坏号拖死整批 |
| T7 | 子进程调用（若有） | 按子进程职责定，且必须 `CommandContext` | 避免孙进程挂死拖住插件 |

**统一要求**：任何 `context.WithTimeout` / `WithDeadline` 的 `cancel` 必须 `defer` 调用，
否则 context 泄漏（连带 timer 泄漏）。

```go
// 反例：cancel 丢了
ctx, _ := context.WithTimeout(parent, 30*time.Second)

// 正确
ctx, cancel := context.WithTimeout(parent, 30*time.Second)
defer cancel()
```

## 六、子进程（孙进程）管理纪律（P0）

插件的子进程是宿主**直接看不到**的（宿主只枚举 `--provider-serve` 的插件进程）。
从宿主视角，它们是「孙进程」，只能通过进程树关系间接回收。

### 6.1 硬约束

| # | 要求 | 原因 |
|---|---|---|
| S1 | 子进程必须是插件的**直接子进程**（`exec.Command` 直接启动），不得 `start` / `nohup` / `setsid` / 双击脚本脱离 | 脱离后宿主 `/T` 树杀覆盖不到，插件死了它还在 |
| S2 | 子进程 stdout/stderr **必须重定向**，不得继承插件标准流 | 见 §3.4，会挂住宿主读 goroutine |
| S3 | 插件退出时必须**主动回收自己的全部子进程**（`Close` 里 kill + wait） | 不能只依赖宿主树杀：插件被 `SIGKILL` 时没有机会清理，但正常退出路径必须自己收 |
| S4 | 子进程数量必须有上限（建议 ≤ 3），且**不得递归拉起**（子进程再拉孙进程） | 宿主后代枚举深度只到 2 层 |
| S5 | 不得拉起**常驻守护进程**（supervisor / while-true 重启循环） | 这类进程会与宿主退避机制叠加；grok 的 supervisor 之所以安全，是因为它由用户开机自启、**不在插件进程树内** |
| S6 | 子进程监听的端口不得固定写死（除非确有需要），且退出时必须释放 | 固定端口在重启时会撞车 |

### 6.2 已知边界（插件作者必须知道）

宿主有两条回收路径，但都有前提：

1. **`taskkill /T`（Windows）**：只覆盖「插件还活着、其父进程已死」的孤儿插件。
   插件自己先崩时，宿主看不到它的子进程（父 PID 已从进程表消失，按 PPID 无根可关联）。
2. **`reapOrphans` 周期扫描**：同样按 PPID 关联，同一个前提。

**因此：插件自身崩溃路径下的子进程回收，主要责任在插件自己** ——
用 `defer`/退出钩子/父进程死亡检测（子进程侧 watchdog）兜住。
宿主不承诺「插件先崩」场景的孙进程回收（详见 `MASTER-orphan-governance.md` C8）。

## 七、日志与状态行纪律（P1）

宿主已有 `PLUGIN-PROVIDERS.md` §10.2 的「stdout 只打状态行」要求，这里补充**容量**视角：

| # | 要求 | 判据 |
|---|---|---|
| L1 | stdout 只打状态行（ready/need_config/fatal），**日志一律走 stderr 或 `data/` 文件** | 契约要求，违反会破坏就绪解析 |
| L2 | stderr 日志必须有**速率控制**：同一错误在短时间内重复时要去重或折叠 | 宿主环形缓冲只有 500 行，狂打日志会把有用信息挤掉 |
| L3 | **单行日志不超过 4KB**（宿主会截断） | 长 JSON/响应体不要整段打进日志 |
| L4 | 落盘日志必须**轮转**（建议 10MB × 5 份 或 按天 + 30 天保留） | `data/` 体积不无限增长 |
| L5 | 日志中**不得出现**完整 token / cookie / 密码 / refresh token（只显示前后 4 位） | 抽查 `data/` 与 stderr 无明文 |
| L6 | 关键错误必须同时进**状态行**（`fatal` 的 `error` 字段）或 `data/` 事件日志，不能只打一行 stderr | 宿主重启后 stderr 环形缓冲会被新周期覆盖 |

## 八、启动与退出纪律（P1）

| # | 要求 |
|---|---|
| B1 | `ready` 必须在 15s 内打出。重活（拉模型、连上游、起浏览器）放到 `ready` 之后异步做，用 `need_config` 或面板状态表达进度 |
| B2 | `need_config` 后**不得退出**，要周期重读配置并补打 `ready` |
| B3 | 退出路径必须**幂等**：被重复 kill、信号重复到达时不 panic、不死锁 |
| B4 | 不得拦截 `SIGKILL`（拦不住），也不要在 `SIGTERM` 里做**长时间**清理（宿主退避只有 30s，可能被强杀） |
| B5 | 退出时必须：停后台 goroutine → 关监听 → 回收子进程 → 刷盘（若有未落盘状态） |
| B6 | 不得自己重启自己（`exec` 自身、while-true 重拉），重启是宿主的职责 |

## 九、验收：插件作者提交前必做的四项测量

这四项不是「建议」，是**交付门槛**。每项都要有实测数据，不接受「应该没问题」。

### 9.1 内存稳定性（24h 或加速压测）

```
基线：启动后 1h 的 RSS / HeapInuse
压测：1000 次 /v1/chat/completions（含 100 次流式）
判定：压测后 goroutine 回到基线 ±10；HeapInuse 增长 < 30% 且回落
```

### 9.2 Goroutine 泄漏

```bash
# 压测前后各一次
curl -s http://127.0.0.1:<plugin>/debug/pprof/goroutine?debug=1 | head -1
```

判定：**数量不随请求数累积**。若某类 goroutine 每次都 +1，就是泄漏。

### 9.3 句柄/连接

```bash
# Windows
handle.exe -p <pid> | wc -l
# Linux
ls /proc/<pid>/fd | wc -l
```

判定：压测前后差值 < 20，且不随请求数线性增长。

### 9.4 子进程清理

```
1. 记录插件及其子进程 PID
2. 正常退出插件（宿主 toggle 关闭）→ 断言：插件与全部子进程消失，端口释放
3. 强杀插件（taskkill /F，不带 /T）→ 断言：插件消失
   （注：此场景宿主不承诺回收孙进程，属已知边界；插件应通过子进程侧
    父进程死亡检测自行退出）
```

## 十、反模式清单（明确不要做）

在 `PLUGIN-CAPABILITIES.md` §8 的 10 条之外，资源维度补充：

1. **每请求 `&http.Client{}`**：连接池与空闲连接永不回收，是 Go 最常见泄漏源之一。
2. **`context.WithTimeout` 不 `defer cancel()`**：timer 泄漏，长跑必炸。
3. **包级 `map[string]*Something` 只增不删**：请求去重表、账号缓存、错误记录的经典形态。
4. **`go func(){ for { ... } }()` 无退出条件**：插件每次重载配置就多一个，永不退出。
5. **`time.NewTicker` 不 `Stop()`**：每次调用泄漏一个 runtime timer。
6. **SSE 聚合后整段返回**：把流式做成非流式，内存随响应长度线性增长，同时失去流式体验。
7. **孙进程继承 stdout/stderr**：挂住宿主读 goroutine，`cmd.Wait()` 永不返回（§3.4）。
8. **孙进程用 `start`/`nohup` 脱离**：宿主树杀覆盖不到，插件死了它还在。
9. **无上限日志**：写 `data/` 不轮转，或往 stderr 狂打（500 行环形缓冲秒满）。
10. **插件自建 supervisor 循环**：与宿主退避叠加，形成双层重启抖动。
11. **把上游错误重试做成无限循环**：429/5xx 必须有次数上限和退避。
12. **在锁内做网络/磁盘 IO**：高并发下直接全插件卡死。

## 十二、宿主侧待补的兜底能力（现状记录）

本文多处写了「宿主不限制」「宿主不承诺」，这些是当前事实，不是设计目标。后续可补：

| 缺口 | 影响 | 建议 |
|---|---|---|
| 无资源限制（Job Object / cgroup） | 插件无限涨内存会拖垮整机 | Windows Job Object 可设内存/进程数上限；需 `golang.org/x/sys`，属外部依赖决策 |
| 无资源监控与告警 | 泄漏只能靠用户感觉「变卡」 | 宿主定期采插件 RSS/句柄数，面板展示趋势，超阈值告警 |
| 「插件先崩」孙进程不回收 | 崩溃路径留残留 | 路线 B：运行期带创建时间的后代快照（见 MASTER C8） |
| 未强制插件暴露 pprof | 泄漏只能黑盒观察 | 约定一个仅本机可访问的调试端口，或提供 `data/` 下的采样文件 |

> 在上述兜底落地前，**本文的插件自律要求是唯一防线**。

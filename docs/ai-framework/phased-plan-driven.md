# 阶段化计划驱动交付（Phased Plan-Driven Delivery）

**项目**: opencode2api_enhance  
**用途**: 人 + 多 AI 协作时的**元规范**——如何切阶段、写计划、交接执行、独立验收。  
**计划实例目录**: `docs/ai-framework/plans/`（若已有 `docs/superpowers/plans/` 可继续用，二者择一为主并在计划里写清）。  
**OpenCode 入口**: `/plan-phase`、`/accept-phase`、`/handoff`（见 `.opencode/commands/`）。

本文件**不是**某一功能的实施计划；实施计划按阶段另存。

---

## 1. 一句话

**先对齐边界 → 写可执行阶段计划（含验收与交接提示词）→ 执行方按 Task 落地并交证据 → 独立验收 → 缺陷写入下一阶段。**

规划/验收与执行宜分离；验收只认证据，不认「应该能过」。

### 1.1 三原则一句话（元规范的第一性原理）
> **任务定义落盘（不丢）→ 进度靠 commit+验收表判定（可恢复）→ 子代理任务幂等（可重放）。**

| # | 原则 | 含义 | 为什么必须 |
|---|------|------|-----------|
| 1 | **任务定义落盘（不丢）** | 所有计划/Task/验收表写进仓库文件（`docs/ai-framework/plans/`），不留在对话记忆里 | AI 会话上下文会丢；换会话/换 AI/重启，落盘的任务定义不丢 |
| 2 | **进度靠 commit+验收表判定（可恢复）** | 进度不以「我记得做到哪」为准，以 **git commit 链 + 验收表打勾状态** 为准 | 任何会话中断/交接，从 commit 历史 + 验收表即可完整恢复现场 |
| 3 | **子代理任务幂等（可重放）** | 交接提示词自包含；同一任务重复执行产出一致，不重复建文件/重复提交/重复计费 | 子代理可能重跑、重试、多代理并行；非幂等会导致重复劳动与冲突 |

**推导**：三原则是八步循环的底层假设——计划落盘（原则 1）→ 执行按 commit 推进（原则 2）→ 交接提示词可重放（原则 3）。任何阶段计划、交接提示词、验收流程违反任一条，即视为不合格。

## 2. 八步循环

> 八步循环的运行方式可选**交互式**（每步等人确认）或**目标模式**（AI 自主连续推进，跑完才停），见 §12。默认交互式。

| 步 | 名称 | 做什么 | 产出 |
|----|------|--------|------|
| 0 | 定边界 | 一句话目标；做/不做；红线（密钥、合规、YAGNI） | 口头约定或 STATUS 数段 |
| 1 | 摸现状 | 分支、与 main 差、**上阶段实际落地产物（接口签名/测试数/文件清单/分支 tip）**、已有能力、单测/产物 | 基线快照 |
| 2 | 写阶段计划 | Task 可 commit；每 Task 有测法 | `docs/…/plans/YYYY-MM-DD-phase-….md` |
| 3 | 写交接提示词 | 贴计划文末，可整段复制 | 「给接手 AI 的完整提示词」 |
| 4 | 执行 | 严格 Task 1→N；小步可审查的 commit | 功能分支 + 提交链 |
| 5 | 执行方自证 | 跑测试/构建，自评验收表 | 命令输出、产物路径 |
| 6 | 独立验收 | 另一会话/角色：对照表 + 复跑 + 红线 | 通过 / 有条件通过 / 不通过 |
| 7 | 下一阶段 | 通过或有条件通过 → 新计划 + 新提示词；缺陷进下阶段 Task 1 | 阶段 N+1 计划 |

> **实事求是**：下一阶段计划必须**贴着上一阶段实际落地产物**来写（真实接口签名、测试数、文件清单、分支 tip），不预先批量写完；未确定的依赖/契约**不写死**。后续阶段依赖前面阶段的真实产物，提前写细必然返工、且易与代码脱节（违客观事实）。

## 3. 角色

| 角色 | 职责 | OpenCode |
|------|------|----------|
| 规划 | 定阶段、写计划与提示词、合并策略 | `@phase-planner` / `/plan-phase` |
| 执行 | 只按计划 Task 实现、自测、交证据 | 外部 AI 或本会话（用计划文末提示词） |
| 审查 | 阶段实现完成、验收前：独立审风格/测试/依赖/架构红线/安全 | `/review` 或独立审查代理 |
| 验收 | 对照验收表（含审查结论）、复跑命令、给结论与下阶段 | `@phase-acceptor` / `/accept-phase` |
| 人类 | 定范围、手工点验、是否 push、是否放宽 | — |

**原则**: 规划方写提示词 → 执行方落地 → 验收方独立判。同一对话既写又做又自判「全绿」风险更高。

与**单次提交审查**（`/review`、`CODE_REVIEW.md`）的区别：审查偏一次 diff；本方法论偏**整阶段**对照验收表。

## 4. 阶段计划必须包含的类别

| # | 类别 | 说明 |
|---|------|------|
| 1 | 元信息 | Goal / Architecture / Tech / **实施档位** / **子代理开关** / 状态 / 分支名 |
| 2 | 全局约束 / 红线 | 冲突时以本节为准；密钥不进 git 等 |
| 3 | 阶段地图 | 前后阶段；本阶段边界 |
| 4 | 文件与契约 | 改哪些文件；配置/API 契约 |
| 5 | **功能 Task** | 有序、可测、可 commit |
| 6 | **测试** | 单测/集成/构建命令与期望 |
| 7 | **代码审查** | 独立角色审查：风格/测试/依赖/架构红线/安全；产出 通过/有条件/不通过（见 §4.2） |
| 8 | **验收标准总表** | 编号 + 通过条件（含代码审查结论条目） |
| 8 | 风险与降级 | 做不完怎么砍 |
| 9 | **交接提示词** | 零上下文可执行 |
| 10 | 残留 / 已知缺陷 | **验证不通过项逐条列出**，写进下阶段 Task 1（见 §4.1） |

主干：**边界 + 功能 Task + 测试 + 代码审查 + 验收表 + 交接提示词**。

### 4.1 不通过项下放机制（硬性，2026-08 实战沉淀）

> 来源：多项目实战规则——「每阶段 = 功能开发 + 测试 + 验证 + 代码审查；任一不通过的部分在下一阶段中明确声明并修复，直到全部完成」。

1. **默认每阶段四件套缺一不可**：功能开发、测试、验证、**代码审查**，全部通过才算阶段完成。若用户因 token 预算选择低档位（见 §4.3 实施档位），按档位执行；**未做项记为「跳过」，不视为「不通过」**——但低调档位 ≠ 全绿，须显式登记为「未执行」。
2. **本阶段不通过项（测试/验证/代码审查任一）→ 逐条写入下一阶段计划开头**，固定小节名「**阶段开头：上阶段遗留**」：
   - 把上一阶段验收表中 ⬜/❌ 的项原文抄入（含代码审查不通过结论）；
   - 每项一句话标注「未通过原因 + 状态 + 来源（测试/验证/审查）」；
   - **下一阶段优先处理这些遗留项，全部回归通过后才允许推进本阶段新功能**。
3. **验收表是流转凭证**：完成一项改 ✅ 并注明日期/验证命令；❌ 项自动流转到下一阶段遗留小节，形成闭环。
4. **有条件通过 ≠ 全绿**：主路径齐备但存在已知缺陷，缺陷必须显式写进下一阶段；禁止假全绿。

### 4.2 代码审查（阶段级强制环节）

> 与提交级 `/review`（单次 diff）互补：**阶段级代码审查**在验收前跑，覆盖本阶段全部提交链。

1. **独立角色**：审查方不参与本阶段实现（同一会话既做又审风险高，同 §3 原则）；OpenCode 可用 `/review` 或独立审查代理。
2. **审查面**（按项目补）：代码风格 / 测试完整性（关键路径有无断言）/ 依赖合理性 / 架构红线（厂商信息不进 core 等）/ 安全（密钥、注入、越权）/ API 契约一致性。
3. **产出**：通过 / 有条件通过（列问题清单）/ 不通过（列阻塞）。问题清单必须进验收表，❌ 项下放下一阶段（§4.1）。
4. **验收联动**：验收结论 = 测试证据 + 审查结论合并；审查「有条件通过」不是放行绿灯，问题须在遗留小节登记。

### 4.3 运行模式、实施档位与子代理（开工前询问，给用户选择权）

> 初衷：框架「四件套缺一不可」与用户 token 预算可能冲突。给用户选择权，让「力度」可调、不问就把用户拖进全流程；子代理也费 token，需一并询问。

**开工前（`/plan-phase` 或规划时）一次问清三件事：**

0. **运行模式**（本项目/大任务走哪种，见 §12）：
   - **交互式**（默认）：每阶段等你确认。
   - **目标模式**：宏观目标已明确时，AI 自主连续推进、跑完才停；等不了的人工验证项标记「待人工」继续；红线仍需授权。

1. **实施档位**（本阶段做多少）：

| 档位 | 做什么 | 四件套 | 说明 |
|------|--------|--------|------|
| 简约 | 功能开发 | 1/4 | 先出功能，无测试/审查证据 |
| 经济 | 开发 + 测试 | 2/4 | 保证基本正确 |
| 全能（**默认**） | 开发 + 测试 + 代码审查 | 3/4 | 标准交付 |
| 豪华 | 开发 + 测试 + 代码审查 + 端到端验证 | 4/4 | 完整交付 |

   默认**全能**；用户预算紧可主动降级；档位可每阶段调整。

2. **是否启用子代理**（只作用于需要「独立角色」的环节——**代码审查 + 验收**）：

| 档位 | 子代理作用范围 | 默认建议 |
|------|--------------|----------|
| 简约 / 经济 | 仅验收（可主会话做，成本低） | **不启用**（省 token） |
| 全能 / 豪华 | 代码审查 + 验收 | **建议启用**（角色独立） |

   - **启用**：审查/验收由独立子代理担任，符合 §3 分离原则；但子代理**费 token**。
   - **不启用**：审查/验收由主会话直接担任，省 token；「写/做/判」同会话，独立性降级、自判全绿风险偏高（同 §3）。
   - **全能/豪华 + 不启用**：必须在计划里**显式写一句**「审查/验收由主会话担任，独立性降级」，让用户知情后再继续。
   - **豪华的端到端验证**：**永远不用子代理**（本就要人工/部署机）。

**记账规则（关键区分）：**
- **不通过项** = 做了但失败（测试/验证/审查任一 ⬜❌）→ 下放下一阶段修复（原机制，见 §4.1）。
- **跳过项** = 因档位/子代理**未做** → 在验收表单独登记「未执行」，**不当作缺陷自动下放**；token 充足时**询问是否补做**（补跑测试 / 补代码审查 / 补端到端验证）。

**底线（无论哪档）：** 验收表如实记录「完成 + 跳过」；低调档位 ≠ 全绿，不得冒充「豪华已通过」。未做的必须显式「未执行」，供后续补做。

### 单个 Task 最小结构

```text
Task N：一句话目标
  Files：创建/修改/测试路径
  行为或契约：做成什么样
  Steps：实现 → 跑哪条命令 → 期望输出
  Commit：一条约定格式的说明（见 AGENTS.md / 项目 Git 规范）
```

## 5. 交接提示词五段结构

文末「给接手 AI」整段必须含：

1. **基线** — 目录、从哪分支拉、已完成阶段、必读计划路径  
2. **做** — 本阶段目标列表（对应 Task）  
3. **不做** — 红线与范围外（抄 Global Constraints）  
4. **工作方式** — 先测基线、按 Task 顺序、证据优先、提交规范、回复语言  
5. **交卷** — 分支名、commit 列表、验收表自评、测试/构建结果、残留风险  

开头建议明确：**完整执行本阶段，不要只写方案。**  
**默认不 `git push`**，除非人类写进计划并授权。

**项目接手 / 中断恢复（做了一半怎么办）**：任何时刻中断、换人、换 AI，按三条恢复现场——
1. 读总控：`MASTER-PLAN.md`（或已定的 MASTER 目标）——明确「整体做到哪、还剩什么」；  
2. 读进度：`git log` 提交链 + 本阶段验收表（✅/❌/跳过）——明确本阶段实际落到哪；  
3. 读未完成：`docs/issue-log/OPEN.md`（未关闭项）——明确剩下什么。  

然后用本节的**五段结构**写一份零上下文提示词交给接手方（人或 AI）即可无缝续做。恢复靠三原则（落盘/commit+验收表/幂等），断点可重入。

## 6. 验收输出四段（强制）

1. **基线** — 当前分支、tip、main 是否已含本阶段  
2. **对照表** — 计划验收表逐项 ✅ / ⚠️ / ❌ + 证据  
3. **结论** — 通过 / 有条件通过（列缺陷）/ 不通过（列阻塞）  
4. **下一步** — 下阶段要点；缺陷必须进下阶段 Task  

**有条件通过合法**：主路径齐备 + 已知缺陷显式写入下一阶段，不假装全绿。

### 6.1 验证分工两层（2026-08 实战沉淀）

避免「计划写了验证项但没人能执行」——每项验证标注责任人：

| 层 | 谁执行 | 内容 | 完成标志 |
|----|--------|------|----------|
| **自动化验证** | 执行方（子代理/同事） | 单测、集成测试、构建、`go test` 全绿、`-race` 关键包、代码走查 | 交付前必须完成，验收表该项打 ✅ |
| **端到端验收** | 用户 / 部署机 / 真机环境 | 挂起节点、并发压测、真机 GUI、CI 三平台产物、docker run、macOS 真机 | 标注「需部署机/用户配合」，由人工执行后打 ✅ |

规则：执行方对自动化验证负全责（不收「自动化没过」的货）；端到端项不得由执行方自评通过——必须人工/环境验证，验收人在验收表确认。

## 7. 阶段切分规则

1. 一阶段一个可演示增量。  
2. 计划内写死「明确不做」。  
3. main 合并、是否 push 写进计划；默认不 push。  
4. 密钥与破坏性操作永远在红线里（按各项目补充，如不提交 `.env`、凭证、私钥）。

## 10. 原则四条

1. **边界先于功能**  
2. **计划必须可交接**（零上下文提示词）  
3. **任务必须可验证**（命令 + 期望）  
4. **验收独立且认证据**（缺陷显式带入下阶段）
5. **验证不通过必下放**（下阶段开头「上阶段遗留」小节显式声明并优先修复）  
6. **验证分工两层**（自动化执行方负责；端到端需部署机/用户配合，不虚假自评）  
7. **实事求是**（下一阶段计划须基于上一阶段实际产物，未确定的依赖不写死）

## 12. 运行模式（Run Mode：交互式 / 目标模式）

> 决定上面的八步循环由**人驱动**还是由 **AI 自主驱动**。默认**交互式**；目标模式需显式开启。

### 12.1 交互式（默认）

每阶段：规划 → （等用户确认）执行 → （等用户确认）验收。节奏偏稳，适合边界/需求仍在讨论、或需人工点验的阶段。**本文主体按此模式描述。**

### 12.2 目标模式（自主，显式开启）

**适用**：宏观目标已明确（如「开发该应用，含 6 个模块」且每模块有完成判据），期间不缺人盯；token 预算内希望**持续跑完、不再打扰**。

**开启前提（缺一不可）**：存在一份 **MASTER 目标**——列全部模块/边界/依赖 + 每模块的「完成判据」+ 全局红线。缺此判据不得开启（否则易跑偏）。

**行为**：
1. **总览先行 + 滚动细化**：先立 MASTER（地图）；每个阶段的详细计划（Task/测试/验收表）**到了才写、才更新**，且**贴着上一阶段实际落地产物**（接口签名/测试数/文件清单/分支 tip）来写（实事求是）；允许「实施中再细化计划」，但 MASTER 的完成判据不变。
2. **自主循环直到完成**：AI 连续执行「计划→实施→自动验证→自主验收→下放」，**不因阶段完成停下等你确认**。
3. **待人工项登记不阻塞**：测试/验证需要真机/部署机/人工时，**只标记「待人工」并继续**，不等待（见 §6.1 端到端层；目标模式下由「回绝等你」改为「登记继续」）。
4. **红线仍需授权**：密钥、破坏性操作、无法自动化解的方向性冲突 → **仍暂停问人**；其余全部自主。
5. **失败与遗留照旧**：自动验证不通过 → 下放下一阶段（§4.1）；代码审查（按档位）照跑。

**终止**：MASTER 目标中每模块完成判据**全部达成** + 无「不通过」项 → 终止，输出两清单：
- **完成清单**（每阶段 ✅ + commit 链）
- **待人工清单**（标记的端到端/真机/部署项；**不算未完成**，交用户收尾）

**诚实边界（硬性）**：
- 目标模式下「**待人工 ≠ 已通过**」；最终状态是「**有条件完成**」，不是「全绿」。禁止把「待人工」当「已验证」。
- 可**随时接管**：任何时刻暂停，由人接手；恢复靠三原则（落盘 + commit/验收表 + 幂等），断点可重入。

### 12.3 与档位/子代理的关系

- 目标模式**不改变档位**：仍在所选档位（简约/经济/全能/豪华）内推进，只是**不停下等你**。
- 子代理：目标模式通常**建议启用**（自主连续跑分阶段更省主会话上下文、更稳）；启用/关闭仍按 §4.3 询问。

### 12.4 如何进入 / 退出目标模式

触发方式（任选其一）：
1. **对话口令（最常用）**：对 AI 说「**进入目标模式**」即开启；说「**退出目标模式，切回交互式**」即回到默认。口令即行为开关，无需专门命令。
2. **开工前询问**：开始一个大任务（或首个阶段）前，框架主动问一句「本次用目标模式（自主跑完）还是交互式（每阶段等你）？」——默认交互式；用户选目标模式后按 §12.2 执行。
3. **一次性命令**（可选）：`/run-goal` 录入 MASTER 目标 + 档位/子代理后自主开跑（若已提供）。

目标模式可**随时中断/切回**：中断即回归交互式；恢复靠三原则（commit/验收表）断点重入。

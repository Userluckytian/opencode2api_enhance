## 1. token 自助餐厅管理后台改造（阶段 Y）

- **类型:** 需求（领导提出）
- **提出人:** 用户（转达领导要求）
- **状态:** 已实现，待人工验收
- **计划:** `docs/ai-framework/plans/2026-10-20-token-shop-admin-insight.md`
- **分支:** `feature/web-self-service`（未提交、未 push）

### 领导原始要求

1. 支持看请求来自哪个 IP，并把同一 IP 的请求汇总到一起（不能一条一条列）。
2. 支持按小时授权：同一 IP 只能使用 1kw token 或 2 小时，哪个先到就报哪个原因给用户并阻止继续使用；管理页可见，领取 token 页面不加相关信息。
3. 支持限制速度（每秒最大 token 输出约 60 个的平均速度）。
4. 要求 2、3 可按 IP 单独设置，不强制全局。
5. 管理页以分析为主：统计 + 合理建议（如每人每周 20KW token 时每天多少合适），并加 AI 问数。

### 实现内容

**缺陷与安全（Task 1）**

| 项 | 说明 |
|----|------|
| 过期 Key 状态 | `handleListKeys` 增 `expired`/`exhausted`/`status`；此前过期 Key 在页面显示「正常」 |
| 改密吊销会话 | `SessionStore.RevokeAllExcept`：改密后旧会话立即失效，保留当前操作者 |
| 登录限速 | `LoginLimiter`：5 次失败/5 分钟 → 锁 1 分钟，按客户端 IP 计数 |
| 日志过滤 | `ReadLogsFilter(date, keyID, ip)`；后端早有 date/key_id，前端此前未接 |
| Key 管理 | 打码 + 显示/复制、状态徽标、搜索/状态筛选/分页、批量删除、清理过期 |
| 上游 Key | 改密码框 + 显示切换 |
| 交互 | `prompt`/`alert`/`confirm` 换成登录表单 + toast + 模态框 |

**IP 治理（Task 2，对应要求 1-4）**

| 项 | 说明 |
|----|------|
| IP 采集 | `clientIP()`：`X-Forwarded-For` → `X-Real-IP` → `RemoteAddr`；**仅当直连对端是回环/私网代理时**才信任转发头，防伪造 |
| 策略存储 | `ip_policies.json`：全局默认 + 按 IP 覆盖（`null`=继承，0=不限） |
| 用量存储 | `ip_usage.json`：窗口用量持久化，进程重启不清零 |
| 窗口判定 | `IPTracker.Check`：窗口内 token 额度与活跃时长**先到先拦**，返回中文原因 + 重置时间 + `Retry-After` |
| 默认策略 | 24h 窗口 / 100 万 token / 120 分钟活跃 / 60 token/s 输出限速（页面可改） |
| 输出限速 | `outputThrottle` 令牌桶：SSE 与非流式均限速；估算 4 ASCII 字符≈1 token、中文 1 字≈1 token；上下文取消立即放行 |
| 拦截留痕 | 被拦截请求也落日志（status=429 + error 原因），可进聚合统计 |
| 领取页 | `index.html`/`app.js` **零改动**，并有单测钉死「领取页不得出现 IP 策略字样」 |

**分析与 AI（Task 3/4，对应要求 5）**

| 项 | 说明 |
|----|------|
| 按 IP 聚合 | `GET /api/admin/logs/aggregate?date=`：请求数/token/Key 数/错误率/被拦截/最近活跃 |
| 概览 | 7 日趋势（请求+token 双柱）、Key 状态分布、活跃 IP、拦截数、错误数、Top IP |
| 配额顾问 | 周预算(万) → 日均(90% 利用率) → 单 IP 日窗口建议，并对比当前默认策略 |

## 5. 领取页下发地址改为本机内网 IP + 消除滚动条（用户实机反馈后）

- **类型:** 缺陷修复 + 体验优化
- **状态:** 已修复并本地复验
- **用户反馈原文:** 「访问地址是 127.0.0.1:xxx/v1，这个不行呀，这个要换成我电脑的 ip，不然别人电脑输入 127.0.0.1:xxx/v1 是访问它自己电脑去了」「点击获取 key，整个的高度有点高了，会出现滚动条，我不想显示滚动条」

### 1）下发的 base_url 不再是 127.0.0.1

**根因**：`HandleCreateKey` 直接用 `r.Host` 拼 base_url。本机测试时 Host 就是 `127.0.0.1:23099`，于是发给别人的地址指向「他自己的电脑」。

**修复**（新增 `web/baseurl.go`）：

`buildBaseURL(publicBase, fwdHost, fwdProto, reqHost, prefix, secure, lanIP)` 按优先级取值：

1. 管理员显式配置的 `public_base_url`（新增配置项，后台「参数设置」可见）——最可靠，末尾自动补 `/v1`（填了也不重复加）；
2. 反代头 `X-Forwarded-Host` + `X-Forwarded-Proto`；
3. 请求自身 Host。

若最终 host 指向本机（`127.0.0.1` / `localhost` / `0.0.0.0` / `::1`），则用**本机内网 IPv4 + 原端口**替换。`lanIPv4()` 遍历网卡，优先私有网段（含 CGNAT 100.64/10），跳过回环/链路本地；探测不到则保持原样。

**实测**：本机 LAN IP `192.168.12.17`，领 Key 下发 `http://192.168.12.17:23099/v1`；显式配置 `http://192.168.12.17:23099` 时下发 `http://192.168.12.17:23099/v1`。

**新增单测** `web/baseurl_test.go`（10 例）：显式配置优先且补 `/v1`、已含 `/v1` 不重复、回环→内网 IP 替换、localhost 替换、转发头优先、前缀保留、TLS 用 https、本机判定、以及端到端「领到的地址不能是本机地址」。

### 2）领取后不再出现滚动条

**根因**：领取后结果区展开，文档高度 705px > 视口 720px 附近，触发滚动。

**修复**（`web/static/index.html`）：

- 收紧全局间距：卡片外边距 56→32、上下内边距 34→30、标题/提示/下拉框/按钮的 margin 逐项压缩；
- 结果区改为紧凑布局：`.row2` 两块间距 12→9px、code 内边距 9→7px、字号 13→12.5px、提示行 12.5→12px；
- 新增两档视口高度自适应：`max-height:780px` 压缩页头与卡片留白；`max-height:680px` 进一步隐藏胶囊标签与页脚、缩小标题与控件。

**实测**：视口 600 / 640 / 680 / 720 / 800 / 900 / 1080 高度下，领取前后均无滚动条；窄屏 420×720 领取后亦无横竖滚动条。

### 验证

`go vet` 通过；`go test ./web/... -count=1` 与 `-race` 全绿；`admin.js`/`app.js` 语法检查通过；浏览器实测下发的 base_url 为内网 IP、七档视口无滚动条、参数设置页新字段可保存且提示当前探测到的内网 IP。

## 11. AI 问数的计量/额度/日志 + 上游密钥脱敏 + 配置审计

- **类型:** 需求（领导要求 5 的延伸）+ 安全加固
- **状态:** 已实现并部署到正式实例

### 需求讨论与结论（先讨论方案，如实回答）

用户提出的原话是：「如果有人拿到了管理员权限，然后是不是可以反代，然后就不受 ip 限制了？…我的想法是，管理员每天有 1kw 的额度上限…ai 问答不保留记录吧？…如果保留，那上下文一长，估计会有问题吧？」

**如实回答（不美化）**：

1. **「后台被拿走后，IP 限制形同虚设」——这个判断成立。** 管理员本来就能改每个 IP 的额度，也能改上游地址。IP 策略是**流量治理工具**，不是**权限边界**。约束管理员自己的额度在架构上没有意义。

2. **但 IP 策略本身的价值不受影响**：它约束的是**领 Key 的普通用户**（真实滥用风险几乎都来自那儿），不防管理员。

3. **「上下文一长会有问题」——当前实现其实不存在这个问题**：每次请求只发 `system`（统计快照）+ 当前这一问，**不带历史**；前端气泡只是显示用，不发给模型。所以 token 消耗恒定。代价是模型「失忆」，无法追问。

4. **上游密钥暴露是真洞（且与后台失窃无关时也有价值）**：改动前 `GET /api/admin/settings` 直接回传 `sk-unified-local` 明文。拿到管理员会话即可拿到它并**直连 40080 无限量用**——这条路完全绕过本服务的 IP 策略。

### ⚠ 顺带发现并修复的真实安全漏洞

实现「按 IP 检测」时发现：**原来的 clientIP 解析可被客户端伪造**。

nginx 原本用 `proxy_add_x_forwarded_for`（**追加**语义）。客户端自带 `X-Forwarded-For: 9.9.9.9` → nginx 变成 `9.9.9.9, 192.168.12.17`。而旧代码按「从右往左跳过私网地址」取值 —— 真实客户端 192.168.12.17 本身是内网，被当作代理跳过，最终取到**伪造的 9.9.9.9**。

后果：改个请求头就能领无限个 Key、绕过 IP 策略、绕过网段白名单。

**三层修复**：

1. **nginx 改为覆盖语义**：`proxy_set_header X-Forwarded-For $remote_addr`（原为 `$proxy_add_x_forwarded_for`），客户端送的头被丢弃；
2. **收紧密信代理范围**：只有显式列入 `trusted_proxies` 的对端（默认仅本机）才采信转发头；直连 18081 一律用 `RemoteAddr`；
3. **引入反代共享密钥**（`X-Proxy-Secret`）：web-server 与 nginx 同机时，直连与反代的 `RemoteAddr` 都是 127.0.0.1，**无法靠对端地址区分**。因此 nginx 转发时带一个共享密钥，web-server 只在密钥匹配（`crypto/subtle` 常量时间比较）时才采信任何转发头。密钥自动生成并写入 `config.json` 的 `proxy_secret`，启动时打印并提示 nginx 怎么配。

旧 nginx 配置同步修复：`D:/nginx/conf/opencode2api-web.conf` 与仓库 `deploy/web-server/nginx/web-server.conf` 均已改为覆盖语义并加 `X-Proxy-Secret`。

## 13. 需求纠正：每个 IP 固定一个 Key，额度每日 08:00 自动重置（无需重复领取）

- **类型:** 需求纠正（上一版理解错了）
- **状态:** 已实现并部署到正式实例
- **用户反馈原文：** 「不是上面的意思。我的意思就每个 ip 就提供 1 个 key，这个 key 每天 8 点自动重置成默认设置的额度，不用每天领取」

### 纠正说明

上一版（第 12 节）把「同一个 ip 仅限领取一个 key」理解成「**一天只能领一次，领第二次就报错 429**」，
于是做了「额度日 + 限领一次」的限制。**这是理解错误**：

| | 上一版（错） | 本版（正确） |
|---|-------------|------------|
| 同一 IP 再点「获取 Key」 | 报错 429「次日 08:00 可再领」 | **返回原来那个 Key**（幂等），不报错 |
| Key 有效期 | 到次日 08:00 失效 | **长期有效** |
| 额度 | 每天要重新领才能用 | **每天 08:00 自动重置回默认额度**，直接继续用 |

### 实现

| 项 | 说明 |
|----|------|
| `Key` 结构 | 新增 `IP`（领取来源）、`QuotaDate`（本次额度所属额度日） |
| `Store.CreateOrGetForIP` | 按 IP 查找并复用已有 Key；没有才新建。返回 `(key, isNew, err)` |
| `Store.RollQuota` | 跨额度日（08:00 边界）把 `TokenUsed` 归零、`Quota` 恢复 `config.token_quota` |
| `Store.ConsumeAt` | 扣减前先做跨日重置 → **用户不重新领取也能继续用**（新增显式时间版本 `ConsumeAt`，便于测试） |
| 网关 | 调用前 `RollQuota` + 扣减用同一时间基准；超额时 429 附带「重置时间」 |
| 领取接口 | 重复领取返回同一个 Key，响应新增 `is_new` / `quota` / `token_used` / `reset_at` |
| 领取页 | 规则文案改为「额度每日 08:00 自动重置回默认额度」「每个 IP 固定 1 个 Key，无需每天重新领取（重复点击会拿回同一个 Key）」；结果区新增提示（新建 / 原有 Key 两种文案） |

## 17. 额度口径澄清 + IP 窗口 token 上限改为不限（方案 A）

- **类型:** 配置调整 + 文案澄清
- **状态:** 已实现并部署到正式实例
- **用户反馈原文:**「窗口长度的作用是什么？窗口 token 上限是 100W 上下文的意思是吗？活跃时常、有什么作用等？」→「走 A。活跃时长上限指的是同一个 ip 的最长使用时间吧？这个 2 小时是怎么计算？从第一次调用开始？」

### 澄清（三个容易误解的概念）

| 配置 | 实际含义 | 不是什么 |
|------|---------|---------|
| 窗口 token 上限 | 该 IP 在一个窗口内的**总消耗上限**（输入+输出累加） | **不是**「单次请求的上下文长度」——上下文多长由上游模型自己的 max context 决定，网关管不了 |
| 窗口长度 | 决定额度**多久清零一次**（1440 分钟 = 一天，08:00→次日 08:00） | 不决定单次请求能用多少 |
| 活跃时长上限 | 该 IP 一天内**所有请求实际耗时的累加**（每次请求从发出到响应结束的真实耗时） | **不是**「从第一次调用起的墙钟时间」——上午 10:00 跑 5 分钟、12:00 跑 3 分钟，累加 8 分钟而非 2 小时 |
| 输出限速 | 每秒最多输出多少 token（令牌桶，容量 1 秒，只管输出不管输入） | 不限制输入速度 |

活跃时长的存在意义：**防慢速占位** —— 脚本挂着流式请求不动，token 涨得慢但连接一直占着，纯 token 额度防不住这种情况。

### 调整（方案 A）

发现配置错配：IP 默认策略的「窗口 token 上限 100W」比「参数设置 → 默认额度（每个 Key）1000W」更紧，
等于额度在 IP 层被提前拦截。**IP 层面的额度已改为 0（不限）**：

- `DefaultIPPolicy()` 的 `WindowTokens` 由 `1_000_000` 改为 `0`；
- 正式实例已通过 `PUT /api/admin/ip-policies/defaults` 落盘生效：
  `{"window_tokens":0,"window_minutes":1440,"max_active_minutes":120,"output_tps":60}`；
- IP 层面只保留与防滥用直接相关的两项：**活跃时长上限**与**输出限速**。

### 顺带：页面上把每个字段的含义写清楚

「默认策略」卡片下方的说明从一句话扩成逐项解释（窗口 token 上限 / 窗口长度 / 活跃时长上限 /
输出限速各一行），并说明「额度通常由参数设置里的默认额度统一控制，这里一般保持 0，避免两处额度错配」。

### 验证

- `go vet` 通过；`go test ./web/... -count=1` 与 `-race` 全绿。
- 正式实例实测：`ip_policies.json` 落盘为 `window_tokens: 0`；IP 表格显示
  「0 / 不限」「重置 次日 08:00」；页面上四个字段的说明均已渲染。

## 19. 额度变更改为「次日 08:00 生效」

- **类型:** 需求
- **状态:** 已实现并部署到正式实例
- **用户反馈原文:**「比如说我设置额度是1kw，然后有3个key已经在使用了，其中一个已经使用
  超过了500W，然后我想要吧额度设置为200W，我希望是次日开始生效，你看看是否可以做？」

### 原行为与问题

保存设置时立刻 `ApplyQuotaDown` 把所有存量 Key 的额度砍到新值。于是当天已用超过
新额度的 Key **当场超额**，下一次请求直接 429 —— 等于用一次配置操作打断别人的工作。
另外「token_quota 不能低于已发放最大额度」的 400 拦截会让管理员**永远调不低额度**
（存量 Key 的额度总是高于新默认值）。

### 实现

| 项 | 改动 |
|----|------|
| 生效时机 | 改为「只更新配置，不动存量 Key」；存量 Key 在跨额度日（08:00）重置时统一恢复为新默认值 |
| `SetDefaultQuota` 同步 | 运行时改额度时同步 `a.Store.SetDefaultQuota(newQuota)` —— 否则跨日重置走 `ConsumeAt` 内部路径时用的是旧值，要等重启才生效 |
| 400 拦截 | 移除。它的理由（误操作砍掉在用 Key 额度）在改为次日生效后已不成立 |
| 立即收紧的出路 | 新增 `POST /api/admin/keys/{id}/quota`，需要立刻收紧某个存量 Key 时用它 |
| 钳制语义 | `ClampOutOfRangeQuota` 上界从 `defaultQuota` 改为 `MaxTokenQuota` —— 原先用 defaultQuota 当上限，启动时会把所有额度高于新默认值的**正常** Key 全砍掉，既让当天 Key 当场超额，又把「次日生效」变成「重启即生效」 |
| 数据竞争 | 修一处：网关读 `a.Cfg.TokenQuota` 未加锁，与设置接口的写构成竞争 |
| 页面 | 「参数设置」补充说明「修改后次日 08:00 生效，当天在用的 Key 不受影响，新领的 Key 立即按新额度发放」；保存时 toast 区分是否改了额度 |

### 验证

- `go vet` 通过；`go test ./web/... -count=1` 与 `-race` 全绿。
- 新增 `TestQuotaChangeTakesEffectNextDay`（改额度当天存量 Key 额度与用量不变、
  仍可继续用；次日 08:00 恢复新默认值且用量归零）与
  `TestNewKeyGetsCurrentQuotaImmediately`。
- 更新两条依赖旧拦截语义的用例（`TestQuotaDowngradeBelowIssuedMaxIsRejected` →
  `...IsAllowed`、`TestAdminPutSettingsRejectsQuotaBelowIssued` → `...AllowsQuotaBelowIssued`）。
- 端到端实测（开发实例，3 个 Key 额度 1000W，k2 当天已用 600W）：
  改额度 1000W→200W 返回 200；**当天三个存量 Key 额度仍 1000W、用量不变**；
  k2 继续调用返回 200（模型正常响应）；**新领的 Key 立即是 200W**。

   `space-bunny` 模型上游已不可用，删除后重新领了 `minimax-m3.1-flash`，
